# Бюджет LLM: лестница и лимиты на запуск

Дата: 2026-10-21 · роль 1 · ветка `vladislav/llm-budget` · ТЗ: ML-3, общее ТЗ р. 8; граница с BE-10 (прогрев, роль 3), F9 (админка, роль 4), ML-13 и ML-15 (агент и чат).

## Что уже есть

Шлюз (задача 3) держит дневной лимит `LLM_DAILY_BUDGET_RUB`: перед вызовом — резерв оценки, после — факт; сверка с `llm_calls` раз в минуту; сутки по МСК. На 100% любой вызов, кроме `essential`, получает `BudgetExceeded`. Нет промежуточных ступеней, лимита на один разбор или чат и данных для админки.

## Цели

- Лестница деградации: шлюз сам отказывает тем вызовам, которые на текущей ступени не положены, а потребители могут спросить ступень заранее.
- Лимиты на запуск: разбор не дороже `INSIGHT_MAX_RUB` (4 ₽), чат — `CHAT_MAX_RUB` (1,5 ₽).
- Админка видит расход за сутки по задачам и моделям и ступень лестницы.

## Не цели

- Сам прогрев, разбор и чат: они вызывают шлюз и реагируют на отказ, это задачи BE-10, 16 и 20.
- Реальная смета суток в `docs/MODELS.md`: нужен день работы с ключом.
- Профиль `local` через Ollama: организаторы не ответили, разрешён ли он.

## Лестница

Ступень считается по факту расхода за сутки (`spent / limit`), без резервов идущих вызовов: резерв — оценка сверху, и ступень не должна мигать от параллельных запросов.

| Ступень | Порог | Что запрещено (кроме `essential`) |
| --- | --- | --- |
| 0 | < 70% | ничего |
| 1 | ≥ 70% | прогрев разборов: `insight_plan`, `insight_write`, `insight_critic` в фоновой полосе; массовые прогоны: `bank_theses`, `chart_read`, `eval_judge` в фоновой полосе |
| 2 | ≥ 85% | плюс судья `rank_judge`; `event_card` в фоновой полосе — только с `priority=True` (официальный источник). «Проверить на своей новости» идёт интерактивной полосой и проходит |
| 3 | ≥ 95% | вся фоновая полоса; `insight_critic` в любой полосе — разбор коротким режимом |
| 4 | ≥ 100% или лимит ≤ 0 | всё: разбор без LLM (ML-14) |

- Ответ из кэша выдаётся на любой ступени: он бесплатный, а прогретый накануне кэш — то, на чём держится день показа.
- Отказ — `BudgetExceeded` (подкласс `LLMUnavailable`, его уже ловят все потребители) с полем `step` и текстом, какая ступень и что запрещено. Строка `llm_calls` на отказ не пишется: вызова не было, как и сейчас при исчерпанном лимите.
- `raw_call` (probe) подчиняется тем же правилам как фоновый вызов задачи `probe`.

## Лимиты на запуск

- `llm_scope(trace_id=…, event_id=…, limit_rub=…)` — новый необязательный аргумент. Агент открывает область с `settings.insight_max_rub`, чат — с `settings.chat_max_rub`.
- Перед каждым платным вызовом в области: потрачено + резервы идущих вызовов области ≥ лимита → `RunLimitExceeded(BudgetExceeded)`. Резерв самого вызова не входит: это оценка сверху (`max_tokens`, ×2 на рассуждения), и с ним первый же шаг разбора на GLM (~3,6 ₽ резерва) не прошёл бы лимит 4 ₽, хотя по факту стоит 1–2 ₽. Лимит запуска поэтому мягкий: перерасход — не больше одного вызова на каждый, начатый параллельно, пока лимит не был занят; строгий лимит держит дневной бюджет.
- Резервная модель после такого отказа не пробуется: цепочка останавливается, агент отдаёт то, что успел проверить, с пометкой (ML-13).
- Кэш в лимит не входит (0 ₽).

## API шлюза

- `gw.json(..., priority: bool = False)` — новый необязательный аргумент, остальное без изменений.
- `await gw.budget_state() -> BudgetState(day, limit_rub, spent_rub, step)` — со сверкой по БД. Для прогрева (роль 3: «если позволяет бюджет»), агента (короткий режим на ступени 3) и админки. Ключ не нужен: ответ без сети.

## Админка

`GET /api/admin/llm/usage` уже в контракте (`LlmUsage`, `ladder_step` 0–4) — это и есть «`GET /llm/state`» из ТЗ, новый маршрут не нужен. Заглушка `LiveBackend.llm_usage` (`ML-3`) заполняется:

- `day`, `budget_rub`, `spent_rub`, `ladder_step` — из `gw.budget_state()`;
- `by_task` — из `llm_calls` за сутки, группировка по задаче и модели: число вызовов (с кэшем), ₽, переключения на резерв (`fallback_from` не пуст, не из кэша), ошибки (`error` не пуст), медиана мс по вызовам не из кэша (кэш с 0 мс исказил бы задержку). Сортировка — по ₽ по убыванию.
- БД недоступна — `by_task` пуст, ступень и расход процесса всё равно отдаются.

Запрос живёт в `app/llm/store.py` (`usage_since`), `live.py` только собирает ответ.

## Решения роли 1

- Граница суток — МСК, как сейчас. Провайдер границу не подтвердил; если она по UTC, сдвиг — 3 часа, а лимит 480 ₽ из 500 оставляет запас на это.
- Ступень — по факту, без резервов (см. выше).
- `bank_theses`, `chart_read`, `eval_judge` останавливаются на 70% вместе с прогревом: это массовые прогоны, которые ТЗ и так велит делать в отдельный день; дневной лимит не даст им перейти 100%, но лестница должна оставить остаток интерактиву.
- `news_filter` и `profile_text` в лестнице не упомянуты — идут до 95%, как прочая фоновая работа: без фильтра лента перестанет пополняться.
- Отказ по лимиту на запуск не пробует резервную модель: лимит считается на весь запуск.
- Лимит запуска мягкий (без резерва самого вызова), дневной — строгий (с резервом): см. «Лимиты на запуск».
- `priority` — флаг вызывающего, а не правило по источнику внутри шлюза: шлюз не знает, откуда публикация.
