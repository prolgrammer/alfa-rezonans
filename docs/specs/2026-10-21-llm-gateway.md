# Шлюз моделей (ML-1)

Дата: 2026-10-21 · роль 1 · ветка `vladislav/llm-gateway` · ТЗ: ML-1, E1 общего ТЗ; граница с ML-2 (probe) и ML-3 (бюджет).

## Зачем

Все вызовы LLM в проекте идут через один шлюз. Тогда белый список моделей (ограничение 04 кейса), дневной бюджет 500 ₽, кэш и учёт расходов находятся в одном месте. Сбой модели не превращается в пустой экран: шлюз уходит на резервную модель, а если не ответила ни одна, поднимает `LLMUnavailable`. Потребитель ловит это одно исключение и переходит на путь без LLM (ML-14).

Сейчас `app/llm/gateway.py` — заглушка, которая всегда поднимает `LLMUnavailable`. Эта задача заменяет её рабочим шлюзом и сохраняет имена, на которые уже опираются `app/api/errors.py` и `tests/boundary/test_stubs.py`.

## Цели

- Вызов модели по имени задачи: `gw.json`, `gw.tools_step`, `gw.vision`. Модель, резерв и параметры задаёт `config/models.yaml`.
- Белый список из шести моделей кейса. Конфиг с другой моделью не загружается, и процесс не стартует.
- Цепочка резервных моделей, предохранитель, повторы на сетевых ошибках, понижение режима JSON.
- Кэш ответов в `llm_cache`: повтор — 0 ₽, `make eval` переигрывается бесплатно.
- Строка в `llm_calls` на каждую попытку модели, в том числе неудачную и из кэша.
- Промпты — файлы с версией в шапке; версия входит в ключ кэша и попадает в `llm_calls`.
- Дневной лимит в ₽ с резервированием оценки до вызова.
- Ключ API не попадает ни в логи, ни в `llm_calls`, ни в текст исключений.
- Все свойства покрыты тестами на фальшивом провайдере (respx), без живого ключа.

## Не цели (другие задачи ROADMAP)

- Лестница деградации 70/85/95/100%, `GET /llm/state`, лимиты на запуск `INSIGHT_MAX_RUB` / `CHAT_MAX_RUB` — задача 4 (ML-3). Шлюз даёт для неё точки опоры: учёт расхода за сутки и область вызовов с суммой потраченного.
- `orientir llm probe` и запись `.models_caps.json` — задача 5 (ML-2). Шлюз только читает этот файл, если он есть.
- Промпты задач (`news_filter`, `event_card` и остальные) — задачи 7 и дальше. Здесь только механизм загрузки промптов и тестовый шаблон.
- Профиль `local` через Ollama: организаторы его пока не разрешили. Конфиг допускает второго провайдера, но не описывает его.
- Эмбеддинги, веб-поиск и Responses API из Пеленга не переносятся: в этом проекте они не нужны.

## Анти-цели

- Код, который обходит шлюз, или потребитель, который знает имя модели.
- Шлюз, который при недоступной модели виснет на минуты: сбой должен быстро превращаться в `LLMUnavailable`.
- Тесты, которые ходят к живому API или требуют ключа.

## Ограничения

- Провайдер — Yandex AI Studio, OpenAI-совместимый API `https://ai.api.cloud.yandex.net/v1`. URI модели — `gpt://<каталог>/<имя>/latest`, каталог передаётся заголовком `x-folder-id` (OpenAI-Project). Опыт Пеленга (2026-10-14…16) учтён:
  - квота — 5 одновременных запросов (при 8 приходит 429);
  - строгий `json_schema`: все поля объекта должны быть в `required`, иначе 400 «all fields must be required»;
  - по умолчанию AI Studio логирует запросы — шлём `x-data-logging-enabled: false`;
  - Qwen3.6 без `reasoning_effort` тратит `max_tokens` на рассуждения и возвращает пустой `content`.
- HTTP — `httpx` (уже в зависимостях), без SDK `openai`: нужны четыре вида запроса к одному эндпоинту `chat/completions`, а обработку ошибок и понижения проще держать в своём коде. Повторы — свой короткий цикл, без `tenacity`.
- Python 3.12, pydantic v2, psycopg 3, jinja2. Без фреймворков для агентов.

## Публичный API

Имена и сигнатуры заглушки сохраняются. Добавления отмечены.

```python
from app.llm import gw, LLMUnavailable, llm_scope

card = await gw.json("event_card", "event_card", {"sources": ...}, EventCardDraft,
                     event_id=42, lane="background")
step = await gw.tools_step("insight_plan", messages, tools, lane="interactive")
chart = await gw.vision("chart_read", "chart_read", png_bytes, ChartReading)

with llm_scope(trace_id="ins-…", event_id=42) as scope:   # добавлено
    ...                                                    # все вызовы внутри помечаются trace_id
scope.cost_rub, scope.calls                                # итог для трассы агента (ML-13)
```

- `gw.json(task, prompt, vars, schema, *, event_id=None, lane="background") -> M`. `prompt` — имя шаблона `config/prompts/<prompt>.md`, `vars` — его переменные. Возвращает провалидированный экземпляр `schema`.
- `gw.tools_step(task, messages, tools, *, lane="interactive") -> ToolStepResult` — один шаг цикла вызова функций. `messages` — сообщения в формате OpenAI, которые собирает агент. Без кэша.
- `gw.vision(task, prompt, image_png, schema) -> M` — картинка уходит частью сообщения (`image_url` с `data:image/png;base64`). Порядок аргументов — как в заглушке, а не как в тексте ML-1: на заглушку уже опираются тесты.
- `gw.strategy(task) -> "tools" | "prefetch"` (добавлено): `tools`, если стратегия задачи `tools` и у её основной модели есть возможность `tools`; иначе `prefetch`. Агент выбирает стратегию по этому ответу (ML-10).
- `ToolCallRequest` получает поле `id`: без него агент не может ответить на вызов сообщением `role=tool` с `tool_call_id`. Модели `ToolSpec`, `ToolCallRequest` и `ToolStepResult` живут в `app/llm/`, а не в `app/contracts/`, поэтому правка не трогает общий контракт.
- `llm_scope(*, trace_id=None, event_id=None)` (добавлено) — контекстный менеджер на `contextvars`. Вызовы внутри получают его `trace_id` и `event_id`, а в объект области накапливаются ₽, токены и список вызовов (задача, модель, мс, ₽, из кэша, резерв). Это нужно трассе агента (ML-13) и пригодится лимитам на запуск в задаче 4. Аргумент `event_id` у `gw.json` перекрывает значение из области.

### Ошибки

Все наследуют существующее `LLMUnavailable`, поэтому `app/api/errors.py` продолжает отдавать 503, а потребители ловят одно исключение.

| Класс | Когда |
| --- | --- |
| `LLMNotConfigured` | нет ключа или каталога; первый же вызов, без запроса к сети и без строки `llm_calls` |
| `BudgetExceeded` | вызов с резервом перейдёт дневной лимит |
| `AllModelsFailed` | ни основная, ни резервные модели задачи не дали валидного ответа |

Неизвестная задача, отсутствующий шаблон и переменная, которой нет в `vars`, — это ошибки программиста (`KeyError` и ошибка jinja2), а не `LLMUnavailable`: они должны падать в тестах, а не тихо уходить в путь без LLM.

## Поведение одного вызова `gw.json`

1. Задача → модель, резерв и параметры. Шаблон рендерится (jinja2, `StrictUndefined`), из шапки берётся версия: `event_card@3`.
2. Ключ кэша — sha256 от URI модели, сообщений, JSON-схемы, температуры, `max_tokens`, флага рассуждений и версии промпта. Попадание в кэш, ответ которого проходит валидацию схемы, возвращается сразу: 0 ₽, строка `llm_calls` с `cached = true`. Если ответ из кэша не проходит текущую схему, значит, схема поменялась: запись считается устаревшей и запрос идёт к модели.
3. Перед платным запросом — проверка бюджета с резервом. Резерв — оценка ₽ сверху: токены промпта по длине (3,5 символа на токен) плюс полный `max_tokens` ответа. Резерв держится до конца вызова, поэтому параллельные вызовы видят резервы друг друга. Обязательные задачи (`essential`) бюджет не останавливает.
4. Запрос идёт через семафор полосы. У провайдера `concurrency` слотов; `interactive_slots` из них зарезервированы под полосу `interactive`, а полоса `background` получает остальные. Разбор по клику и чат не стоят в очереди за фоновым прогревом.
5. Режим JSON модели — лучший из её возможностей: `json_schema` (строгая схема: все поля в `required`, необязательные — с `null`; `null` у необязательных полей перед валидацией убирается, и pydantic подставляет умолчание) → `json_object` (схема дописывается в промпт) → схема только в промпте. Если провайдер отвечает 400 на `response_format`, режим понижается на ступень, запоминается для этой модели до перезапуска процесса, и запрос повторяется. Так же 400 на `reasoning_effort` отключает этот параметр для модели.
6. Рассуждения выключены везде, кроме задач с `reasoning: true`. Для моделей с `reasoning_off: reasoning_effort` шлём `reasoning_effort: "none"`.
7. Ответ разбирается с починкой: убрать `<think>…</think>` и ```-обёртку, при ошибке взять текст от первой `{` до последней `}`, убрать висячие запятые. Затем валидация pydantic. Не прошла — один повтор: в диалог добавляются ответ модели и текст ошибки валидации. Не прошёл и повтор — модель считается неудачной.
8. Ответ без `{` (пустой или отказ текстом) — сразу неудача модели, без повтора: тот же запрос даст то же самое за те же деньги.
9. Повторы на сетевых ошибках, таймауте, 429 и 5xx — до 3 попыток на модель с паузой 1 → 2 → 4 с; при 429 пауза равна `Retry-After`, но не больше 10 с. Потом модель считается неудачной.
10. Неудача модели → следующая модель цепочки `[model, *fallback]`. В строке `llm_calls` удачной резервной модели `fallback_from` — основная модель задачи.
11. Предохранитель на модель: 5 неудач подряд размыкают его на 60 с. Пока он разомкнут, модель пропускается, если в цепочке после неё есть другая; последнюю модель цепочки пробуем всегда. Через 60 с идёт один пробный запрос: успех замыкает предохранитель, неудача снова размыкает на 60 с. Состояние держится в памяти процесса.
12. Успех — ответ в кэш, строка `llm_calls`, расход в бюджет и в область `llm_scope`. Неудачные попытки тоже стоят денег: их токены и ₽ записываются в `llm_calls` и в бюджет.

**Решения по деталям (роль 1):**

- *Что считается неудачей модели.* Предохранитель считает неудачи модели, а не HTTP-попытки: одна неудача — это вызов, который после своих сетевых повторов и повтора валидации не дал ответа (сеть, 5xx, 429, таймаут, невалидный JSON дважды, ответ без JSON). 400, которое удалось обойти понижением режима, неудачей не считается.
- *Время.* У каждой полосы есть общий дедлайн вызова на всю цепочку моделей: `background` — 180 с, `interactive` — 40 с (разбор по ML-13 укладывается в 45 с). Таймаут попытки — `min(timeout_s провайдера, остаток дедлайна)`. Новую попытку или новую модель не начинаем, если до дедлайна меньше 3 с. Истёк дедлайн — `AllModelsFailed`.
- *Резерв бюджета* берётся на каждую попытку модели по её цене и освобождается сразу после неё; фактический расход по `usage` списывается и для неудачной попытки. Если `usage` не пришёл, токены оцениваются по длине. `completion_tokens` берётся целиком, вместе с токенами рассуждений. У задач с `reasoning: true` резерв на ответ — `2 × max_tokens`: рассуждения у части моделей не входят в `max_tokens`.
- *`vision`*: `prompt` — имя шаблона, он рендерится без переменных. Ответ кэшируется, в ключ кэша входит sha256 картинки.
- *`tools_step`*: без кэша; `prompt_version` в `llm_calls` пустой — сообщения собирает агент, а версии своих промптов он пишет в трассу сам.
- *Где живут имена.* Ошибки — в `app/llm/errors.py`, модели шага инструментов — в `app/llm/types.py`. `app/llm/gateway.py` реэкспортирует их, чтобы старые импорты (`app/api/errors.py`, `tests/boundary/test_stubs.py`) не сломались. `LLMNotConfigured` — наследник `LLMUnavailable`.

`tools_step` и `vision` проходят те же шаги, кроме кэша (у `tools_step`) и разбора JSON (у `tools_step` ответ — текст и вызовы функций). `tools_step` идёт только по моделям цепочки, у которых есть `tools`; если таких нет — `AllModelsFailed`. Аргументы вызова функции приходят строкой JSON: шлюз разбирает её, а при ошибке разбора отдаёт `args = {}` и пишет предупреждение — проверку аргументов делает агент (ML-10).

## Учёт: `llm_calls` и `llm_cache`

- Одна строка `llm_calls` на каждую попытку модели (удачную, неудачную, из кэша): `task`, `model` (ключ из белого списка), `prompt_version`, `tokens_in`, `tokens_out`, `cost_rub`, `ms`, `cached`, `fallback_from`, `error` (замаскированный, до 500 символов), `lane`, `trace_id`. Колонки уже есть в `0001_init`.
- Запись идёт сразу после попытки, отдельным коротким запросом с таймаутом 3 с. Ошибка БД не роняет вызов модели: предупреждение в лог, учёт остаётся в памяти. Фоновая очередь, как в Пеленге, не нужна: она требует запуска и остановки в жизненном цикле `api` и `worker`, а это код роли 3.
- Если `TEST_DATABASE_URL` / `DATABASE_URL` недоступен, шлюз работает с кэшем и учётом в памяти.
- `llm_cache`: `key`, `task`, `model`, `response`. Токены в кэше не храним: строка из кэша стоит 0 ₽.
- **`event_id`.** Миграция `0002_llm_calls_event` добавляет в `llm_calls` колонку `event_id BIGINT NULL REFERENCES events (id)` и индекс по ней. По ней считаются стоимость события и смета суток по статьям (ML-3). Значение берётся из аргумента `gw.json` или из `llm_scope`. Таблица `llm_calls` — запись только шлюза, но `migrations/` принадлежит роли 3: правка — добавление необязательной колонки, в PR отмечена для роли 3.

## Бюджет (минимум для ML-1)

- Лимит `LLM_DAILY_BUDGET_RUB` (480). Сутки — по московскому времени. Граница суток у провайдера не известна (вопрос из общего ТЗ р. 16); МСК даёт одинаковые сутки для команды и для отчётов.
- Потрачено за сутки — сумма в памяти; не чаще раза в минуту она сверяется с `SUM(cost_rub)` из `llm_calls` за сегодня, и берётся большее значение. Так учитываются вызовы второго процесса (`worker` и `api`).
- Лестница деградации и `GET /llm/state` — задача 4; она будет строиться на этом же классе.

## Безопасность ключа

- Ключ живёт только в `Settings.llm_api_key` (`SecretStr`) и в заголовке `Authorization: Api-Key …` HTTP-клиента.
- Все тексты ошибок, которые идут в лог, в `llm_calls.error` и в сообщение исключения, проходят маскировку: ключ и каталог заменяются на `***`, так же как `Api-Key …` / `Bearer …` и URI вида `gpt://<каталог>/`.
- Тест: провайдер отвечает 401 и 500 с ключом в теле ответа, а ключ не появляется ни в `caplog`, ни в строках `llm_calls`, ни в `str()` исключения.

## Промпты

- Файл `config/prompts/<имя>.md` начинается с шапки:

  ```
  ---
  task: event_card
  version: 3
  ---
  ```

  Шапка обязательна: шаблон без неё или без `version` — ошибка. Шапка в текст промпта не попадает.
- Шаблоны — jinja2 с `StrictUndefined`. `{% include "_style.md" %}` работает: шапку отрезает загрузчик.
- Версия промпта — `<имя>@<version>`; она в ключе кэша и в `llm_calls.prompt_version`. Правка промпта без смены версии кэш не сбросит: ключ кэша включает и текст промпта.

## Тесты

Все тесты — на respx, ключ фальшивый. Тесты с БД — по образцу `tests/db/` (нужен `TEST_DATABASE_URL`, иначе пропуск).

- Конфиг: репозиторный `models.yaml` загружается; модель вне белого списка, неизвестная задача и ссылка на несуществующую модель — ошибка загрузки.
- Резерв: основная модель отвечает 503 → ответ резервной, `fallback_from` в строке учёта; таймаут → резерв; невалидный JSON дважды → резерв.
- Повтор с ошибкой валидации: первый ответ не проходит схему, второй проходит — одна модель, две попытки.
- Понижение JSON: 400 на `json_schema` → запрос с `json_object` → 400 → схема в промпте; режим запоминается.
- Строгая схема: в запросе все поля в `required`; `null` у необязательного поля даёт умолчание.
- Предохранитель: 5 неудач → модель пропускается; через 60 с (подменённые часы) — пробный запрос.
- Полосы: при занятых фоновых слотах интерактивный вызов проходит.
- Кэш: второй одинаковый вызов не идёт в сеть, `cached = true`, 0 ₽; другая версия промпта — промах.
- Бюджет: необязательная задача сверх лимита — `BudgetExceeded`; два параллельных вызова с резервами не переходят лимит вместе; обязательная задача проходит.
- Маскировка ключа (см. выше).
- Без ключа — `LLMNotConfigured` без запросов к сети.
- `tools_step`: вызовы функций разбираются с `id`; модель без `tools` пропускается.
- `vision`: картинка уходит частью `image_url`.
- `llm_scope`: `trace_id` попадает в строки учёта, сумма ₽ совпадает со строками.
- Учёт в БД: строки `llm_calls` пишутся для удачи, неудачи и кэша; `event_id` из аргумента и из области попадает в строку.
- `tests/boundary/test_stubs.py`: проверка «заглушка поднимает `LLMUnavailable` с ML-1» меняется на проверку «без ключа — `LLMUnavailable`».
