# Probe моделей

Дата: 2026-10-21 · роль 1 · ветка `vladislav/llm-probe` · ТЗ: ML-2 (probe), граница с ML-1 (шлюз) и ML-3 (бюджет).

## Зачем

Шлюз выбирает режим JSON (`json_schema` → `json_object` → схема в промпте) и стратегию агента (`tools` / `prefetch`) по возможностям модели. Сейчас эти возможности заявлены в `config/models.yaml` по памяти и по Пеленгу; для четырёх из шести моделей не проверены даже URI. Probe — разовая проверка на живом ключе, после которой шлюз опирается на факты, а `models.yaml` правится по ним.

Что показала документация AI Studio на 2026-10-21 (до прогона):

- DeepSeek V4.1 Flash есть в каталоге под собственным URI `deepseek-v4.1-flash`, контекст 1 048 576. Прежний `deepseek-v4-flash` — это V4, а не модель белого списка, и он отключается 15.11.2026.
- Qwen3.6 35B принимает картинки (Base64) — кандидат в резерв `chart_read`.
- Gemma 4 26B A4B, GLM-5.3-Flash, Kimi-K2.6 и Qwen3-VL-30B-A3B в публичном каталоге и тарифах не значатся. Либо организаторы дают другой эндпоинт, либо модели подключены их ключу отдельно. Отсюда требование к probe: не только проверить заявленный URI, но и показать, какие модели провайдер реально отдаёт.

## Цели

- `orientir llm probe` проверяет каждую модель `models.yaml` (или выбранные `--model`): доступность по URI, простой ответ, `json_schema`, `json_object`, вызов функции, картинку, рассуждения по умолчанию и параметр их отключения, задержку, токены, стоимость.
- Результат — `.models_caps.json` в корне репозитория; шлюз читает из него итоговые возможности.
- `--dry-run` печатает план вызовов и смету сверху, без ключа, сети и БД.
- Итог на экране — таблица и список расхождений с `models.yaml`, по которому конфиг правится руками.
- Все вызовы — через шлюз: бюджет, маскировка ключа и строка `llm_calls` (задача `probe`) на каждый.

## Не цели

- Автоматическая правка `models.yaml`: конфиг правит человек по отчёту, чтобы правка прошла ревью.
- Бенчмарк качества — задача 21 (ML-2, день 9).
- Уточнение цен: probe цен не видит, цены — по тарифам AI Studio.
- Смена провайдера или схемы авторизации: если организаторы дадут не AI Studio, это отдельная правка шлюза.

## Проверки

Для каждой модели последовательно (параллельные вызовы исказили бы задержку). Все вызовы — `temperature 0`, `max_tokens` задачи `probe` (300: хватает, чтобы увидеть рассуждения, и дёшево).

| Проверка | Запрос | Успех |
| --- | --- | --- |
| `simple` | «Столица Франции? Одно слово», без параметра рассуждений | ответ содержит «Париж» / «Paris». 404, 403 (модель не подключена каталогу) или «модель не найдена» → модель недоступна, остальные проверки пропускаются; 401 → прогон останавливается (ключ неверен) |
| `reasoning_off` | тот же запрос с `reasoning_effort: "none"` | параметр принят (не 400). Вместе с `simple` даёт: рассуждает ли модель по умолчанию и гасит ли их параметр |
| `latency` | `simple` ещё два раза в рабочем режиме шлюза | медиана трёх `simple` — задержка модели |
| `json_schema` | «Назови столицу Франции и её население» — **без** слова JSON в промпте, `response_format: json_schema` по строгой схеме | ответ разбирается и проходит схему: значит, схему применяет провайдер, а не догадка модели |
| `json_object` | «Верни JSON-объект с полями city и country…», `response_format: json_object` | парсер шлюза получает объект с `city`; обёртка в ```` ``` ```` отмечается в заметке |
| `tools` | вопрос о ключевой ставке и функция `get_key_rate(country)`, `tool_choice: auto` — как в шлюзе | вызван `get_key_rate` с непустым `country` |
| `vision` | PNG 64×64, левая половина красная, правая зелёная (картинка собирается в коде); «какого цвета левая и правая половины» | названы оба цвета. Две половины, а не один цвет: угадать сложнее |

«Рабочий режим шлюза» — тот, в котором шлюз будет звать модель: если модель рассуждает по умолчанию и принимает `reasoning_effort`, проверки после `simple` идут с ним, иначе без.

Результат проверки трёхзначный: `true` — работает, `false` — не работает (4xx на параметр, кроме 403, 408 и 429; ответ не тот; текст вместо функции), `null` — неизвестно (таймаут, 429, 5xx, сеть; ответ оборван по `max_tokens` — это сбой прогона, а не отсутствие возможности). `null` не меняет заявленное: временный сбой не должен отнимать у модели возможность.

Рассуждения видны по `reasoning_content` / `reasoning` в сообщении или `usage.completion_tokens_details.reasoning_tokens > 0`; признак — `finish_reason: "length"` с пустым ответом (как Qwen3.6 без `reasoning_effort`). Провайдер может рассуждения скрыть, поэтому без явного признака probe смотрит на токены ответа «Париж»: больше 40 — рассуждала, до 15 — нет, между — `null` («не ясно», рекомендации по `reasoning_off` нет). Параметр, после которого модель всё равно рассуждает, считается непринятым.

## Каталог провайдера

Перед проверками — `GET {base_url}/models` теми же заголовками. Если провайдер отдаёт список, probe печатает модели, похожие на белый список (сравнение по имени без регистра и знаков), и для каждой модели конфига — есть ли её URI в списке. Ответ не 200 или не список — строка «каталог недоступен», проверки идут дальше. Вызов бесплатный, в `llm_calls` не пишется.

## Файл `.models_caps.json`

```json
{
  "probed_at": "2026-10-22T09:15:00+03:00",
  "models": {
    "qwen3.6-35b-a3b": {
      "probed_at": "2026-10-22T09:15:00+03:00",
      "uri": "gpt://{folder}/qwen3.6-35b-a3b/latest",
      "status": "ok",
      "caps": ["json_object", "json_schema", "tools", "vision"],
      "reasoning_default": true,
      "reasoning_off_param": true,
      "latency_ms": 820,
      "checks": {"json_schema": {"ok": true, "ms": 910, "tokens_in": 40, "tokens_out": 22, "note": ""}}
    }
  },
  "catalog": ["qwen3.6-35b-a3b", "deepseek-v4.1-flash"]
}
```

- `uri` — шаблон из конфига, без каталога: файл можно показать кому угодно.
- `status`: `ok`, `unavailable` (URI не найден), `error` (не удалось проверить).
- `caps` — итог: заявленные в `models.yaml`, плюс `true`, минус `false`, `null` не трогает. Для `unavailable` и `error` — заявленные без изменений.
- Запуск с `--model` обновляет только эти модели, остальные записи сохраняются; у каждой модели своё время проверки. Файл пишется через временный и `os.replace`: шлюз соседнего процесса не прочтёт половину.
- Шлюз читает `models.<имя>.caps`; файл в другом формате или битый — предупреждение в лог и заявленные возможности (как сейчас).
- Файл в `.gitignore`: он зависит от ключа и окружения, а проверенные возможности переносятся в `models.yaml` — его и коммитим.

## Бюджет и учёт

- Вызов идёт через новый метод шлюза `Gateway.raw_call(model, messages, *, response_format, tools, reasoning_off)` — без кэша, резерва модели и предохранителя (probe проверяет конкретную модель, а не задачу), но с резервом бюджета, слотом провайдера, маскировкой и строкой `llm_calls` (`task = "probe"`, ошибка — в `error`). Метод — только для probe, в `__all__` не входит. Рядом — `Gateway.check_configured()` (нет ключа → `LLMNotConfigured` до открытия БД) и `Gateway.provider(name)` для запроса каталога.
- Все вызовы прогона — под одним `trace_id` `probe-<время>`: стоимость прогона — один запрос к `llm_calls`.
- Дедлайн вызова — 60 с (фоновая полоса, повторы провайдера на 429/5xx как обычно).
- Смета `--dry-run` — сверху: на модель 7 вызовов (`simple` ×3, `reasoning_off`, `json_schema`, `json_object`, `tools`) плюс `vision`; вход оценивается по тексту запросов (картинка — 2000 токенов, как в шлюзе), выход — `max_tokens`. При текущих ценах конфига — до 20 ₽ на все шесть моделей; по факту в разы меньше: короткие ответы не доходят до `max_tokens`.

## Команда

```
orientir llm probe [--dry-run] [--model NAME ...]
```

- Без ключа (`LLM_API_KEY`, `LLM_FOLDER_ID`) — сообщение и код 1; `--dry-run` ключа не требует.
- Неизвестная модель в `--model` — ошибка параметра.
- 401 или исчерпанный дневной бюджет — остановка с кодом 1; модели, проверенные до остановки, в файл записываются: деньги на них уже потрачены.
- Иначе — файл пишется, код 0, даже если часть моделей недоступна: это результат, а не сбой.
- Вывод: каталог, таблица (модель, статус, четыре возможности, рассуждения, задержка, ₽), затем «Расхождения с models.yaml» — что убрать или добавить в `caps`, что поменять в `reasoning_off`, какие URI недоступны.

## Решения роли 1

- Probe проверяет картинку у всех моделей, а не только у VL: по документации Qwen3.6 принимает изображения, и это резерв для `chart_read`.
- `json_schema` проверяется промптом без слова JSON: иначе модель ответит JSON и без поддержки схемы, и проверка ничего не докажет.
- `null` не отнимает заявленную возможность: probe на неудачной минуте не должен понижать шлюз.
- `.models_caps.json` не коммитится, проверенное переносится в `models.yaml`.
- DeepSeek переводится на `deepseek-v4.1-flash` с контекстом 1 048 576 по документации AI Studio. Суффикс `/latest` оставлен, как у Qwen3.6, для которого он проверен в Пеленге; probe проверит и его.
- У Qwen3.6 в `caps` добавляется `vision` по документации; резерв `chart_read` меняется только после прогона.

## Что остаётся после этой задачи

- Живой прогон сделан 2026-10-21, итог и правки `models.yaml` — в `docs/MODELS.md`. AI Studio на модель, не подключённую ключу, отвечает 400 «Failed to get model»: probe считает это недоступностью, а шлюз — виной модели, чтобы предохранитель её отключал.
- Если четырёх моделей нет у провайдера — вопрос организаторам, где они доступны; шлюз под другой эндпоинт — отдельная задача.
