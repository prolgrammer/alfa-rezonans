# Тезисы банка из аналитических материалов (ML-6, B6)

Дата: 2026-10-22 · роль 1 · ветка `vladislav/bank-theses`

## Зачем

Позиция банка — обязательный блок разбора (ограничение 02 общего ТЗ). Её источник — тезисы, извлечённые из PDF аналитики банка: короткое утверждение с дословной цитатой и страницей. Тезис попадает к агенту (`get_bank_view`) только после вычитки человеком, а до неё проходит проверку кодом: цитата есть на странице, числа тезиса есть в цитате, факторы — из каталога.

## Границы

Входит: `extract_theses(doc_id)`, проверка тезисов, запись в `bank_theses`, повторный прогон без оплаты, `get_bank_view(factor)` из БД, список тезисов и отметка вычитки для админки, выгрузка и загрузка вычитки через CSV, смета прогона.

Не входит: разбор PDF (BE-7 роли 3 — пока заглушка на фикстуре), прогон по 9 документам (задача 10), `chart_read` (Should, отложен), экран вычитки (роль 4).

## Вход

`doc_chunks(doc_id) -> list[BankChunk]` — фрагменты документа со страницами. Пока заглушка до BE-7 роли 3: фрагменты из `tests/fixtures/bank_chunks.json`. Метаданные документа (название, дата публикации) берутся из `bank_docs`: строка там нужна и для внешнего ключа `bank_theses.doc_id`. Документа нет в `bank_docs` — `NotFound`.

## Промпт и вызов

- Фрагменты одной страницы склеиваются в один источник в порядке `id`; номер источника `n` — номер страницы. Страницы идут не подряд (пустые выпадают), поэтому блоки собираются через `wrap_source(page, …)` — тот же примитив, на котором стоит `render_sources`.
- На страницу — до `PAGE_LIMIT = 6000` символов, на документ — до `DOC_LIMIT = 240 000` символов (≈ 80 тыс. токенов). Что не влезло, модель не видит; страницы сверх предела отбрасываются целиком и пишутся в лог.
- Документ целиком — один вызов задачи шлюза `bank_theses` (DeepSeek-V4.1-Flash, резерв Qwen3.6 35B). `max_tokens` поднят с 4000 до 6000: до 20 тезисов с цитатами и числами в 4000 не укладывались бы.
- Промпт `config/prompts/bank_theses.md` с `{% include "_sources.md" %}`, каталог факторов целиком, до `THESES_MAX = 20` тезисов.

Схема ответа модели (`ThesesDraft`) — поля `BankThesis` без ограничений длины и с `factors` строками: длины и id проверяет код, иначе одна длинная строка роняла бы весь ответ. `kind`, `direction`, `horizon` — перечисления контракта, их держит строгая схема.

## Проверка кодом

Каждый тезис проверяется отдельно; тезис принимается или получает список ошибок.

1. `text` непустой, обрезается до 500 символов по слову; все проверки чисел идут по обрезанному тексту.
2. Цитата: не короче `QUOTE_MIN` (10 символов) и есть дословно (`find_quote`) на странице `page`. Если цитата нашлась на других страницах, а на указанной нет, код ставит первую страницу, где она есть: где стоит цитата, код знает точнее модели, а интерфейс откроет именно её. Цитата длиннее 600 символов обрезается после проверки (префикс проверенной цитаты остаётся дословным).
3. Числа текста: каждое число из `text` должно стоять в цитате с тем же масштабом (тыс, млн, млрд, трлн — сокращением или полным словом) и тем же признаком процента. Годы и даты — тоже числа: тезис «снижение в 2027 году» требует 2027 в цитате.
4. `numbers[]`: значение по модулю есть в цитате как целое число (по границам чисел), с масштабом из `unit` и с «%», если в `unit` процент (`unit_matches`).
5. `factors`: только id из `config/factors.yaml`, без повторов, до 5. Неизвестный id — ошибка, но тезис с оставшимися факторами выживает; без единого известного фактора тезис не принимается.
6. Повтор тезиса (та же страница и та же нормализованная цитата или тот же нормализованный текст) отбрасывается молча.

Для пунктов 3–4 в `app/text/verify.py` добавлена `number_marks(text)` — множество `(значение, масштаб, процент)` по всем числам текста. `unit_matches` переписан поверх неё без смены поведения, кроме одного уточнения: «процентный пункт» больше не считается процентом (раньше «на 1 процентный пункт» проходило как 1 %, а `п. п.` — нет).

## Перегенерация

Если хоть один тезис не прошёл, делается один повторный вызов: модели показываются провалившиеся тезисы и их ошибки (через `neutralize`, как в карточке события), и она возвращает только исправленные версии этих тезисов или пропускает их. Принятые с первого раза тезисы не пересылаются и не теряются. Что не прошло и во второй раз, удаляется. Сбой модели на перегенерации не отменяет принятого с первого раза.

## Хранение и повторный прогон

- `bank_theses`: `payload` — `BankThesis` в JSON, `factors`, `kind`, `page`, `published_on` из `bank_docs`, `verified`, `prompt_version` вида `bank_theses@1`.
- Если у документа уже есть тезисы с текущей версией промпта, `extract_theses` отдаёт их без вызова модели. `force=True` перестраивает.
- Новый прогон заменяет тезисы документа целиком в одной транзакции. Отметка вычитки переносится на новый тезис, если у него та же страница, та же цитата и тот же текст (после нормализации): иначе человек проверял другое утверждение.
- Документ без единого принятого тезиса строк не оставляет; его повторный прогон снова идёт к шлюзу, но одинаковые запросы шлюз отдаёт из своего кэша без оплаты.
- Один документ одновременно строится один раз (замок на документ в процессе).

## Вычитка (`verified`)

ТЗ не говорит, кто ставит `verified`. Решение: код его не ставит никогда.

- `NULL` — не вычитан (так записывается каждый новый тезис), `true` — верно, `false` — неверно.
- Отметка ставится человеком: экран админки (`GET /api/admin/theses`, `POST …/verify` — `LiveBackend` теперь зовёт `list_theses` и `set_verified`) или CSV, который команда вычитывает вместе с ролью 2: `python -m app.bank.theses export <файл.csv> [--doc N]` выгружает тезисы с колонкой `ok`, `python -m app.bank.theses apply <файл.csv>` загружает отметки (`1/да/+` — верно, `0/нет/-` — неверно, пусто — без изменений). Команда в `orientir` не добавлена: `app/cli.py` — файл роли 3.
- Агент видит только `verified = true`.

## `get_bank_view(factor, limit=3)`

Из БД: только `verified = true`, фактор в `factors`, свежие первыми (`published_on DESC`, затем `id`). Название документа — из `bank_docs`. Строка, чей `payload` не проходит текущий контракт, пропускается с предупреждением в логе.

MOCK-режим API читает фикстуры: `MockBackend` переключён на `fixture_bank_view` — прежнюю заглушку, оставленную под этим именем. Тесты инструментов агента без БД подменяют `get_bank_view` той же функцией.

## Сбой LLM

`LLMUnavailable` (нет ключа, бюджет, все модели упали) не роняет `extract_theses`: в лог идёт предупреждение, в БД ничего не пишется, возвращаются тезисы, уже сохранённые для документа (любой версии; возможно, пустой список). Следующий прогон попробует снова. Ошибка кода и отмена поднимаются наружу.

## Смета

`estimate_theses(doc_ids)` — верхняя оценка в рублях до вызова: промпт рендерится как для настоящего вызова, входные токены считаются оценкой шлюза, выходные — по `max_tokens`, цена — основной модели; перегенерация не входит (оценка одного вызова на документ). Для этого в шлюз добавлен публичный `Gateway.estimate_json(task, prompt, vars, schema)` поверх той же оценки, что идёт в резерв бюджета.

## Проверка

- Модульные тесты проверки: цитата на странице и исправление страницы, короткая цитата, число внутри другого числа (`4%` в `14%`), масштаб (`млн` против `млрд`, полные слова), процент против рубля, процентный пункт, диапазон, год в тексте, неизвестный фактор, повтор.
- Тесты потока на фальшивом шлюзе: одна перегенерация только провалившихся тезисов, удаление после второго провала, сбой на перегенерации.
- Тесты с БД: запись и повторный прогон без вызова, `force`, перенос вычитки, сбой LLM без потери прежних тезисов, `get_bank_view` (только вычитанные, свежие первыми, лимит), CSV туда и обратно, `set_verified`.
- Живой прогон на `bank_chunks.json` (5 документов) со сметой заранее.

## Риски

- Таймаут провайдера 60 с: на настоящем документе в 30–80 тыс. токенов ответ DeepSeek может не уложиться. Проверяется в задаче 10 на первом PDF; при необходимости — поднять таймаут задачи или делить документ.
- Цитата из таблицы PDF может не найтись дословно из-за разбивки ячеек: такие тезисы удалятся. Видно по логу удалённых в задаче 10.
