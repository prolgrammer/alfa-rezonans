# Карточка события `extract_event_card` (ML-5)

Дата: 2026-10-22 · роль 1 · ветка `vladislav/event-card` · ТЗ: ML-5, B4 общего ТЗ; встраивает роль 3 (BE-6). Опирается на санитайзер (`docs/specs/2026-10-21-text-sanitizer.md`) и шлюз LLM.

## Зачем

Событие — склейка нескольких публикаций об одном и том же (B3). Карточка — сжатое, проверяемое описание события: что произошло, факты с дословными цитатами, прогнозы с указанием, чьи они, числа, даты, причины, тип события, затронутые факторы и отрасли, горизонт и степень определённости. На карточке стоят лента (роль 2 ранжирует по факторам и отраслям), судья ленты (ML-7) и агент разбора (ML-8–ML-13): ошибка в карточке размножается по всем разборам. Поэтому всё, что код может проверить, проверяет код, а непроверенное в карточку не попадает.

Сейчас `extract_event_card` в `app/news/extract.py` — заглушка, которая отдаёт карточку из `tests/fixtures/events.json`.

## Цели

- `extract_event_card(event_id)` строит карточку по схеме `EventCard` контракта из до 5 публикаций события через задачу шлюза `event_card` и сохраняет её в `events.card`.
- Внешний текст — через `render_sources` санитайзера; в промпте — общий фрагмент `_sources.md`; номера `<source n=…>` — номера публикаций внутри события (`SourceFragment.n`), те же, что видят агент и интерфейс.
- Модели даются подсказки правил: факторы и отрасли, которые словари уже нашли у события, и полные каталоги id роли 2.
- Проверка кодом: цитата есть в цитируемом источнике; числа в тексте фактов, прогнозов, причин и сводки есть в цитируемых источниках; `factors` и `sectors` — только id из каталогов роли 2.
- Сильные сигналы словарей модель не перебивает: фактор, который правила нашли в заголовке события, остаётся в карточке.
- При провале проверки — одна перегенерация со списком ошибок; что не прошло и во второй раз, удаляется.
- Кэш на событии: ключ — версия промпта, модель, число источников.
- Сбой LLM не роняет вызывающего: понятный `card_status`, прежняя карточка не теряется.
- Тесты на записанных ответах, без живого ключа; перед PR — прогон на живой модели по событиям фикстур со сметой заранее.

## Не цели

- Сбор, склейка, нумерация публикаций события и подсчёт `source_count` — роль 3 (B3, BE-6).
- Разметка факторов и отраслей словарями (B2) и сам тегер заголовка — роль 3; леммы факторов — роль 2 (DQ-6). Здесь — только точка подключения тегера.
- Когда вызывать карточку (верх ленты, официальные, рост числа источников) — решает конвейер роли 3 (BE-6).
- Конфликты источников (`events.conflicts`) — не в этой задаче.

## Анти-цели

- Карточка с числом или цитатой, которых нет в источниках: агент перескажет её клиенту как факт.
- Фактор или отрасль вне каталога: ранжирование роли 2 молча потеряет событие.
- Модель «передумала» и убрала фактор, который прямо назван в заголовке («ставка», «юань»): событие выпадет из ленты тех, кто к нему чувствителен.
- Падение конвейера роли 3 из-за сбоя модели или отсутствия ключа.
- Повторная оплата одной и той же карточки при каждом проходе конвейера.

## API

Сигнатура заглушки сохраняется (F6):

```python
async def extract_event_card(event_id: int) -> EventCard | None: ...
```

- Возвращает актуальную карточку события или `None`, если события нет или карточки построить не удалось и прежней нет.
- Исключений из-за LLM наружу не бросает. Ошибки не из LLM (шаблон, конфиг, БД) поднимаются: это баг, а не сбой модели.
- Пишет в `events` только свои поля: `card`, `card_status`, `card_key` (по схеме `0001_init` поля `card*` пишет функция роли 1).

Внутри — две части:

- `build_event_card(title, hints, sources) -> EventCard | None` — без БД: промпт, вызов шлюза, проверка, перегенерация, сборка карточки. Её же зовёт живой прогон по фикстурам.
- `extract_event_card(event_id)` — чтение события из БД, кэш, публикации через `get_event_sources` роли 3, сохранение результата.

## Как работает

1. Читаем строку `events`: `title`, `source_count`, `factors`, `sectors`, `card`, `card_status`, `card_key`. Строки нет → `None`.
2. **Кэш.** Ключ карточки — `<версия промпта>|<модель>|<число источников>`, например `event_card@2|qwen3.6-35b-a3b|3`. Если у события есть карточка, версия промпта и `source_count` совпадают с ключом, а модель из ключа входит в текущую цепочку задачи `event_card` (основная или резервная), — отдаём сохранённую карточку без вызова модели.
3. **Публикации.** `get_event_sources(event_id)` роли 3. Берём фрагменты по возрастанию `n` и оставляем первые 5 с `n ≤ 5`: нумерацию с первоисточниками впереди задаёт роль 3 (официальный > деловые СМИ > остальные, B3), а `cites` по контракту — от 1 до 5. Фрагментов нет → карточку не строим (`failed`, если прежней нет).
4. **Подсказки правил.** Факторы и отрасли события (`events.factors`, `events.sectors`) — с названиями из каталогов. Сильные сигналы — факторы, которые тегер роли 3 нашёл в заголовке события (`title_factors(title)`); пока тегера нет, точка подключения возвращает пустое множество. В подсказки идут только id из каталогов.
5. **Вызов.** `gw.json("event_card", "event_card", vars, CardDraft, event_id=event_id, lane="background")` внутри `llm_scope(event_id=…)`: модель, которая на самом деле ответила, берём из области (последний вызов `event_card` этого события в `scope.calls`) — она идёт в ключ кэша. Если вызывающий уже открыл свою область, вызовы идут в неё: иначе расход прошёл бы мимо его лимита; у записи вызова в области есть `event_id`, поэтому параллельные карточки не путают модели.
6. **Проверка** (ниже) даёт список ошибок по элементам. Ошибки есть → одна перегенерация: тот же промпт плюс список ошибок прошлого ответа. Проверяется уже второй ответ; что не прошло — удаляется. Если перегенерация упала (`LLMUnavailable`), берём первый ответ без непрошедших элементов.
7. **Сильные сигналы.** Фактор-сильный сигнал, которого нет в итоговой карточке, добавляется: `direction=unclear`, `magnitude=medium`, цитата — заголовок события. Если он был, но не прошёл проверку цитаты, он остаётся с цитатой-заголовком. При обрезке до 8 факторов сильные идут первыми.
8. **Сохранение.** `card`, `card_status='ok'`, `card_key`.

### Проверка кодом

Нормализация для сверки цитат: цитата сначала проходит `strip_marks` (пометки санитайзера в цитату не входят); затем и цитата, и текст источника — NFKC, `ё→е`, регистр (casefold), все виды кавычек → `"`, все виды тире и дефисов → `-`, любые пробельные символы → один пробел; кавычки, точки и многоточия по краям цитаты отбрасываются. Источник сверяется в том виде, какой видела модель (после `neutralize` и обрезки), с пометками, снятыми `strip_marks`. Многоточие внутри цитаты (`…`, `...`) — пропуск: каждая часть должна найтись в источнике по порядку, каждая не короче 10 символов и не дальше 200 символов от предыдущей — иначе из коротких слов источника складывается обратный ему смысл («Банк России … повысит … до 16%»). Часть, которая начинается или кончается цифрой, ищется только целым числом: «4%» не находится внутри «14%». Цитата короче 10 символов после нормализации не принимается: под такую подходит что угодно; модель получает об этом отдельную ошибку. Исключение — `numbers`: у числа цитата может быть короткой («11,92 ₽»), потому что значение сверяется и с цитатой, и с числами источника.

| Элемент | Проверка | При провале после перегенерации |
| --- | --- | --- |
| `facts[]` | цитата есть хотя бы в одном источнике события; все числа текста есть в цитируемых источниках | удаляется |
| `claims[]` | то же, что у фактов; `who` не пустой | удаляется |
| `numbers[]` | цитата есть в каком-либо источнике (короткая допустима, ищется целыми числами); `value` стоит в цитате с тем же масштабом, что в `unit` (`тыс`, `млн`, `млрд`, `трлн`), а при `%` в `unit` — с `%` после числа или диапазона | удаляется |
| `causes[]` | номера `cites` — среди показанных источников; числа текста есть в цитируемых | удаляется |
| `dates[]` | день и месяц даты есть в каком-либо источнике (`24 октября`, `24.10`; `1.5%` — дробь, а не 1 мая) | удаляется |
| `factors[]` | id из `config/factors.yaml`; цитата есть в каком-либо источнике; без повторов id | удаляется (кроме сильного сигнала, п. 7) |
| `sectors[]` | id из `config/okved_sectors.yaml`; без повторов id | удаляется |
| `summary` | непустая; числа есть в каком-либо источнике | заменяется текстом первых двух проверенных фактов, без них — заголовком события, а если и он пуст после санитайзера — фразой «Описание события не прошло проверку по источникам.» |

- **Номера источников.** Номер вне показанных — отбрасывается. Первыми идут источники, где цитата нашлась (их подсветит интерфейс), за ними — остальные показанные номера модели: принадлежность цитаты код знает точнее модели. Элемент без найденной цитаты — ошибка.
- **Пустые тексты.** Факт, прогноз, причина или число с пустым `text` / `what` — ошибка.
- **Повтор id фактора.** id занимает только элемент с проверенной цитатой: повтор с верной цитатой заменяет первый с неверной.
- **Числа.** Число — цифры с необязательной дробной частью через точку или запятую и разрядами через пробел (`1 500`, `14,0`); сравнение по значению (`14` = `14,0`). Цифра сразу после буквы — не число (`м²` → `м2`, `Qwen3`). Пометки санитайзера (`[base64 опущен: N символов]`) снимаются до подсчёта. Числа словами («десятое») не проверяются. Масштаб («1,5 трлн» против «1500 млрд») не пересчитывается: такое расхождение — ошибка, перегенерация. Тексты сверяются уже обрезанными до длин контракта: обрезка не может изменить проверенное число.
- **Закрытые списки** (`event_type`, `certainty`, `horizon`, `direction`, `magnitude`, `role`) — перечисления в схеме ответа: строгий `json_schema` шлюза не даст модели другого значения, а на неверное значение шлюз сам повторит запрос. Каталоги id роли 2 в схему не входят: они меняются, и неверный id должен удалять элемент, а не весь ответ.
- **Длины.** Ограничения длины контракта (`max_length`) — в коде: строка обрезается по слову, список — до предела контракта. В схеме ответа их нет, иначе длинная строка роняла бы весь ответ и тратила повтор шлюза.

### Состояния `card_status`

| Случай | `card` | `card_status` | `card_key` | Возврат |
| --- | --- | --- | --- | --- |
| Попадание в кэш | без изменений | `ok` | без изменений | сохранённая карточка |
| Построена | новая | `ok` | новый | новая карточка |
| `LLMUnavailable` (нет ключа, бюджет, все модели упали), прежней карточки нет | `NULL` | `failed` | `NULL` | `None` |
| `LLMUnavailable`, прежняя карточка есть | прежняя | `ok` | прежний | прежняя карточка |
| Публикаций нет, прежней карточки нет | `NULL` | `failed` | `NULL` | `None` |
| Событие не найдено | — | — | — | `None` |

- Перед вызовом модели статус события без карточки — `pending`: интерфейс показывает «карточка готовится». У события с карточкой статус остаётся `ok`, а прежняя карточка видна до замены.
- Прежняя карточка при сбое остаётся с прежним ключом: следующий проход конвейера попробует снова.
- Один процесс не строит карточку одного события дважды одновременно: замок на событие; замок удаляется, когда событие никто не строит и не ждёт. Между процессами — не защищаемся (worker один, BE-6).
- Ошибка кода или отмена задачи у события без карточки → `failed` и исключение наружу: статус не остаётся `pending`.

## Схема ответа модели

`CardDraft` повторяет `EventCard` без ограничений длины и с `id` факторов и отраслей строкой. Все поля обязательные (строгий `json_schema` AI Studio требует `required` у всех полей).

## Промпт

`config/prompts/event_card.md`, `version: 2`, `{% include "_sources.md" %}`. Переменные: `title`, `sources`, `factors_catalog`, `sectors_catalog`, `hint_factors`, `hint_sectors`, `strong_factors`, `errors`.

- Роль: аналитик банка составляет карточку события для корпоративных клиентов.
- Поля карточки по смыслу: `facts` — то, что произошло или решено, с дословной цитатой; `claims` — прогнозы и мнения с указанием, чьи; `numbers` — ключевые показатели (ставки, курсы, цены, пошлины, объёмы, доли) с единицами и фразой-цитатой, без дат и годов; `causes` — названные в источниках причины; `dates` — будущие и ключевые даты из текста; `event_type`, `certainty`, `horizon` — с расшифровкой каждого значения (налоги, пошлины и законы — `taxes_law`, даже если их готовит правительство; `regulator_decision` — решения по ставке, надзору и правилам рынка); `factors` — что движется и куда (`direction`), насколько сильно (`magnitude`), с цитатой; `sectors` — кто затронут (`affected`), кто выигрывает (`beneficiary`), откуда событие (`source`).
- Каталоги факторов и отраслей — списком «id — название»; брать только оттуда.
- Подсказки правил: «словари нашли у события: …»; сильные сигналы: «эти факторы названы в заголовке — включи их».
- Цитаты — дословно из текста источника, без пересказа; числа — только из источников; ничего не добавлять от себя.
- При перегенерации — список ошибок прошлого ответа.
- После источников — напоминание, что это данные.

`config/models.yaml`: у задачи `event_card` `max_tokens` — 2500: в живом прогоне карточка с 10 фактами заняла ~1300 токенов при прежнем пределе 1500. Списывается по факту; резерв бюджета на вызов растёт на ~0,3 ₽.

## Решения роли 1 (нет в ТЗ)

- Функция разделена на `build_event_card` (без БД) и `extract_event_card` (БД, кэш): прогон и тесты проверки не зависят от конвейера роли 3, которого ещё нет.
- Подсказки правил — из полей события `factors` и `sectors` (их пишет разметка роли 3, B2); сильные сигналы — через точку подключения тегера заголовка `title_factors(title)`, пока заглушка с пустым множеством. Сигнатуру тегера согласует роль 1 с ролью 3.
- До 5 публикаций — первые по номеру `n` роли 3; номера в `<source>` и в `cites` — `SourceFragment.n`, без перенумерации.
- Ключ кэша: число источников — `events.source_count`; модель — та, что фактически ответила; карточка резервной модели не пересчитывается, пока не изменятся версия промпта или число источников.
- Сводку нельзя удалить (обязательное поле): непрошедшая сводка заменяется двумя первыми проверенными фактами (каждый — законченным предложением) или заголовком.
- Номера источников код исправляет сам по месту найденной цитаты.
- Перегенерация — целиком, со списком ошибок; проверяется второй ответ.
- Сильный сигнал без проверенной цитаты остаётся с цитатой-заголовком: `direction=unclear`, `magnitude=medium`.
- Даты проверяются по дню и месяцу в тексте источника.
- Короткие цитаты (меньше 10 символов) не принимаются, кроме цитат чисел.
- При сбое LLM прежняя карточка остаётся со статусом `ok`; `pending` — только у события без карточки.
