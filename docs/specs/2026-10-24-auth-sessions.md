# Вход, сессии и тестовые учётки (BE-9)

Дата: 2026-10-24 · роль api · ветка `exssssii/auth-sessions` · ТЗ: BE-9, р. 10 («Вход и сессии»), р. 3 (вход тестовой учёткой).

## Зачем

Без входа боевой режим (`MOCK=0`) целиком отвечает 401 или 503: сессии нет, `company_name` и `has_company` на заглушке, `orientir seed` не реализован. Компания и роль во всех маршрутах берутся только из сессии, поэтому вход — первое, что нужно живому API.

## Цели

- `orientir seed` создаёт и обновляет тестовые учётки из `config/demo_accounts.yaml`; пароль у всех — `DEMO_PASSWORD`, хеш argon2id.
- Вход: случайный токен в httpOnly-cookie `orientir_session`, в БД — только его SHA-256; CSRF-токен на сессию.
- Блокировка учётки на 15 минут после 5 неверных паролей подряд.
- `/api/me`, `/api/auth/logout`, `/api/demo/switch` работают на сессии из БД.
- `company_name` и `has_company` в `LiveBackend`.
- Журнал `audit_log`: вход, неудачная попытка, блокировка, выход, переключение клиента.
- Режим MOCK не меняется: одна сессия в памяти, тот же `mock-csrf-token`.

## Не цели

- Регистрация, смена пароля, сброс блокировки из интерфейса.
- Отбор демо-компаний из CSV (`scripts/pick_demo_clients.py`) и загрузка CSV (DQ-1).
- Ограничение частоты запросов по IP.

## Учётки

`config/demo_accounts.yaml`: `companies` — словарь «ID → имя для интерфейса» (в CSV имён нет), `accounts` — список с `login`, `company_id`, `user_role`, `access`, `interests`. `company_id` обязателен у всех, включая эксперта и администратора: с него начинается показ. Загрузчик проверяет значения по перечислениям контракта и каталогу факторов и падает с понятной ошибкой.

`seed` идемпотентен: `INSERT … ON CONFLICT (login) DO UPDATE` переписывает хеш, компанию, роль, права, интересы и сбрасывает `failed_logins` и `locked_until`. Сессии пересеянных учёток удаляются: после смены пароля старые cookie не действуют. Учётки, которых нет в файле, не трогаются. Команда печатает таблицу логинов без пароля.

Пока профиль в боевом режиме читается из фикстур, в файле — компании фикстур `C-DEV-01` и `C-IT-01`.

## Сессия

| Что | Как |
|-----|-----|
| Токен | `secrets.token_urlsafe(32)` в cookie; в `sessions.token_hash` — hex SHA-256 |
| CSRF | `secrets.token_urlsafe(32)` в `sessions.csrf_token`, отдаётся в `/api/me` и ответе входа; сверка `secrets.compare_digest` |
| Срок | `expires_at = now() + SESSION_TTL_HOURS`, без продления; истёкшая — 401, строка удаляется |
| Cookie | `HttpOnly`, `SameSite=Lax`, `Secure` при https, `Path=/`, `Max-Age` = TTL |
| Контекст | `company_id = acting_company_id ?? users.company_id`, `user_role = acting_user_role ?? users.user_role`, `access = users.access` |

Вход всегда создаёт новую сессию; если запрос пришёл со старой cookie, её строка удаляется. Истёкшие сессии чистятся при каждом входе.

## Вход и блокировка

1. Учётка по логину. Нет такой — проверка пароля по фиктивному хешу (время ответа то же) и 401 «Неверный логин или пароль».
2. `locked_until > now()` — 429 `rate_limited` с минутами до разблокировки, даже при верном пароле; пароль не проверяется.
3. Неверный пароль — одним `UPDATE` счётчик +1; на пятой ошибке `locked_until = now() + 15 минут`, счётчик в 0. Ответ 401 тот же, что для неизвестного логина; на пятой — 429.
4. Верный пароль — счётчик в 0, `locked_until` в NULL; хеш пересчитывается, если параметры argon2 изменились.

Хеш argon2id считается вне соединения с БД и не больше четырёх одновременно: иначе поток входов занял бы весь пул и память. Поэтому обе записи из шагов 3 и 4 условные — только пока учётка не заблокирована. Если параллельная попытка успела её заблокировать, ответ 429 и сессия не создаётся: пачкой одновременных запросов лимит не обойти. Введённый неизвестный логин в журнал не пишется — в поле логина нередко по ошибке набирают пароль.

Выбор клиента (`acting_*`) учитывается, только пока у учётки права эксперта или администратора.

429 выдаёт, что логин существует; для стенда с тестовыми учётками это приемлемо, а пользователь понимает, почему не пускает.

## Маршруты

- `POST /api/auth/login` — `Me` и cookie; 401, 422, 429.
- `POST /api/auth/logout` — удаляет строку сессии и cookie; CSRF обязателен.
- `GET /api/me` — из сессии.
- `POST /api/demo/switch` — эксперт и администратор; `has_company` и запись `acting_company_id`, `acting_user_role` в строку сессии.

Зависимость сессии одна для обоих режимов: в MOCK — сессия из памяти, в боевом — из БД. Маршрутам режим не виден.

## LiveBackend

- `company_name(ctx)` — имя из `companies` файла учёток, иначе сам ID.
- `has_company(id)` — ID есть в файле учёток или в таблице `companies`.

## Проверка

- Тесты с БД: вход, неверный пароль, блокировка на пятой попытке и 429 при верном пароле, сброс счётчика после успеха, истёкшая сессия, выход, CSRF, переключение клиента экспертом и запрет клиенту, `seed` идемпотентен и сбрасывает блокировку.
- Тесты MOCK остаются зелёными без изменений.
- `orientir openapi --check`.
